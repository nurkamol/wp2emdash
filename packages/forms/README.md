# @wp2emdash/forms

Website forms for [EmDash](https://docs.emdashcms.com/) sites on Cloudflare Workers:

- **Form endpoint** — `POST /api/forms/<id>`: honeypot, rate limit, Cloudflare Turnstile (fails closed), validation
  against the form's own fields (nothing else in the request is read), email through Brevo, Resend, Postmark, SendGrid,
  Mailgun or EmDash's own email pipeline (Settings → Email). Works with and without JavaScript. Field values never
  reach logs.
- **Outbox (optional)** — when email is not set up or the provider refuses, the message is kept in Workers KV instead of
  being lost, retried by the Worker's cron, deleted once emailed or after the retention period. A hold switch keeps
  everything and sends nothing (for a provider that accepts mail but does not deliver it).
- **Keep sent (optional, 1.4)** — a full inbox: every message is kept, also once emailed, with its delivery status
  (Emailed / Waiting / Failed), until the retention period ends. Off by default — a data-retention decision (below).
- **Form messages admin page** — an EmDash native plugin (Block Kit, no React bundle), **admins only**: inbox with
  search, filters, read state and bulk actions; insights (messages per day and per form, from counts only); CSV/JSON
  export through one-time links; import of exported files; activity log; dashboard widget; **Settings**: who form
  messages are emailed to, and **chat notifications** (below).
- **Chat notifications (optional)** — a new message pings Telegram, Slack or a generic webhook (Discord, Google Chat,
  Teams workflows, Make/Zapier/n8n — and WhatsApp through those) with a link to it in Form messages. Off until an admin
  turns a channel on and its Worker secret exists; never delays or fails a submission.

Requires EmDash ≥ 1.5 on the Cloudflare adapter (Workers Paid). Generated by and maintained in the
[wp2emdash](../../README.md) kit; the kit's scaffold wires all of this into every migrated site automatically. The
steps below are for any other EmDash project.

## Install

The package is not on npm. Copy `packages/forms` into the project (for example to `packages/forms`) and add it:

```jsonc
// package.json
"dependencies": { "@wp2emdash/forms": "link:./packages/forms" }
```

Or build a tarball from the kit (`pnpm --dir packages/forms pack`) and `pnpm add ./wp2emdash-forms-1.7.0.tgz`.
The package ships TypeScript source; the site's Astro/Vite build compiles it.

## Wire it up

**1. The endpoint** — `src/pages/api/forms/[id].ts`:

```ts
import { createFormEndpoint } from "@wp2emdash/forms/endpoint";
import type { FormDefinition } from "@wp2emdash/forms";
import contact from "../../../forms/contact.json";

const forms = new Map<string, FormDefinition>([[contact.id, contact as FormDefinition]]);
export const prerender = false;
export const POST = createFormEndpoint({ getForm: (id) => (id ? forms.get(id) : undefined) });
```

A form definition (`FormDefinition`): `id`, `title`, `submitLabel`, `successMessage`, `fields` (`name`, `label`,
`type`, `required`, `options`, `autocomplete`, and per type below), optional `notice` and `afterSubmit` (`"hide"` |
`"reset"`). Field types:

| Type | Renders | Posts | Checked |
|---|---|---|---|
| text, email, tel, number, url, date, textarea | one input | the value | length; email/tel format |
| select, radio | a select / a fieldset of radio buttons | the chosen option | one of `options` |
| checkbox | a checkbox | anything = "Yes" | — |
| consent | a checkbox whose label is `labelParts` (text runs; links kept only when http(s) or site-relative — `safeHref`) | anything = accepted | required → must be ticked |
| signature | a signature pad plus "type your full name" (below) | `<name>` PNG data URL and/or `<name>_typed` | PNG or typed name |
| content | `content` blocks (paragraphs, list items, headings, rules; bold, italic, safe links) — not an input | nothing | — |
| file (1.7) | a file input (`accept`, `maxMb` ≤ 25, `maxFiles` ≤ 5) | the file(s) | extension in `accept` ∩ the built-in list, size, first bytes; stored privately, emailed as a one-time link (below) |

Any field can have `showIf: { field, equals: [...], not? }` (shown only while another field has — or, with `not`, has not
— one of the values; a ticked single checkbox counts as `"yes"`) and `step` (0-based; the definition's `steps: [{ title }]`
names them). The page script shows one step at a time with Back/Next and hides conditional fields (their inputs are
disabled, so not sent); without JavaScript everything shows. The endpoint judges the conditions on the submitted values
(`logic.ts`): a hidden field is neither required nor emailed. Conditional fields are never `required` in the HTML.

Rich text (`labelParts`, `content`) is data, never HTML: pages render it as elements (`@wp2emdash/forms/rich` has
`safeHref` and the converters), so nothing in a definition is inserted as markup.

The page renders the form itself and posts `multipart/form-data` to
`/api/forms/<id>` with the fields, `_hp` (an empty honeypot input, visually hidden) and `cf-turnstile-response`
(the Turnstile widget); send `Accept: application/json` for a JSON answer (`{ ok, message, errors? }`), or let the
browser post and come back with `?form=sent|error`.

**2. The admin page** (with the outbox) — `astro.config.mjs`:

```js
import { formsPlugin } from "@wp2emdash/forms";
// …
emdash({ database: d1({ binding: "DB" }), storage: r2({ binding: "MEDIA" }), plugins: [formsPlugin()] }),
```

**3. The cron** (with the outbox) — the Worker entry (`src/worker.ts`, `"main"` in `wrangler.jsonc`):

```ts
import { env } from "cloudflare:workers";
import handler, { createScheduledHandler, PluginBridge } from "@emdash-cms/cloudflare/worker";
import { type ChatEnv, flushChat } from "@wp2emdash/forms/chat";
import { type CrmEnv, flushCrm } from "@wp2emdash/forms/crm";
import { flushOutbox, type OutboxEnv } from "@wp2emdash/forms/outbox";

export { PluginBridge };
const emdashScheduled = createScheduledHandler();
export default {
	...handler,
	scheduled: async (controller, workerEnv, ctx) => {
		ctx.waitUntil(flushOutbox(env as unknown as OutboxEnv).catch(() => {}));
		ctx.waitUntil(flushChat(env as unknown as ChatEnv).catch(() => {})); // chat notification retries
		ctx.waitUntil(flushCrm(env as unknown as CrmEnv).catch(() => {})); // CRM / mailing-list retries (backoff)
		return emdashScheduled(controller, workerEnv, ctx);
	},
} satisfies ExportedHandler;
```

with `"triggers": { "crons": ["*/5 * * * *"] }`.

## Configuration (`wrangler.jsonc`, per environment — environments do not inherit)

| Name | Kind | What |
|---|---|---|
| `EMAIL_PROVIDER` | var | `brevo` (default), `resend`, `postmark`, `sendgrid`, `mailgun`, or `emdash` (EmDash's own email pipeline, below) |
| `EMAIL_API_KEY` | secret | The provider's API key (`wrangler secret put EMAIL_API_KEY`); not used with `emdash` |
| `FORM_FROM` | var | Sender, e.g. `Site <noreply@example.com>` — verified in the provider account; not used with `emdash` (the sender is set in Settings → Email) |
| `FORM_TO` | var | Default recipients, comma-separated. An admin can replace them on the Form messages page (Settings tab); that setting wins |
| `FORM_LIVE_HOST` | var | Single-environment sites: the production host (`example.com`, `www.` ignored). A message sent from any other host — the workers.dev address before go-live, a Workers preview URL after it — is a **test**: subject prefixed `[Test]`, stored with `test: true`, emailed only to `FORM_TEST_TO`, never to `FORM_TO` or the admin's recipients (also when the outbox cron or "Email it now" sends it later, i.e. after go-live). Unset: every message is real (sites with a staging environment) |
| `FORM_TEST_TO` | var | Test inbox for test messages, comma-separated (kit.config `email.stagingTo`). Unset: test messages are kept in the outbox unsent, or refused (503) without one |
| `MAILGUN_REGION` | var | `eu` for EU Mailgun accounts |
| `TURNSTILE_SITE_KEY` | var | Turnstile widget site key (for the page) |
| `TURNSTILE_SECRET_KEY` | secret | Turnstile secret |
| `FORM_LIMITER` | ratelimits binding | `{ "name": "FORM_LIMITER", "namespace_id": "<unique integer>", "simple": { "limit": 5, "period": 60 } }` |
| `FORM_OUTBOX` | kv_namespaces binding | Turns the outbox on (and with it the admin page's data) |
| `FORM_OUTBOX_DAYS` | var | Retention, 1–90 days (default 30) |
| `FORM_OUTBOX_HOLD` | var | `"1"`: keep every message, send none |
| `FORM_OUTBOX_KEEP_SENT` | var | `"1"`: keep every message, also once emailed (a full inbox, below). Needs `FORM_OUTBOX` |
| `TELEGRAM_BOT_TOKEN` | secret | Chat notifications → Telegram (below). Unset: Telegram is not offered |
| `SLACK_WEBHOOK_URL` | secret | Chat notifications → Slack incoming webhook (`https://hooks.slack.com/services/…`). Unset: Slack is not offered |
| `CHAT_WEBHOOK_URL` | secret | Chat notifications → generic webhook (any `https://` address). Unset: not offered |
| `FORM_WEBMCP` | var | `"0"`: no WebMCP annotations (kit.config `forms.webmcp: false`). Unset: on (below) |
| `FORM_CHAT` | var | `"0"`: no chat notifications on this site (kit.config `forms.chat: false`) |
| `FORM_SENSITIVE` | var | `"1"`: the site handles sensitive data (kit.config `sensitiveData`) — chat notifications are notification only, CRM sync impossible |
| `BREVO_API_KEY` | secret | CRM sync → Brevo contacts. Unset: Brevo uses `EMAIL_API_KEY` when `EMAIL_PROVIDER=brevo`, else it is not offered |
| `HUBSPOT_TOKEN` | secret | CRM sync → HubSpot contacts: private app token, scope `crm.objects.contacts.write`. Unset: not offered |
| `MAILCHIMP_API_KEY` | secret | CRM sync → Mailchimp audience members (`…-us21`). Unset: not offered |
| `MAILCHIMP_SERVER_PREFIX` | var | Optional: the Mailchimp data center (e.g. `us21`) when the key has no suffix |
| `FORM_CRM` | var | `"0"`: no CRM sync on this site (kit.config `forms.crm: false`) |
| `FORM_CRM_PRESELECT` | var | Providers pre-selected for every form until an admin saves (kit.config `forms.crm.providers`); with `FORM_CRM_BREVO_LIST`, `FORM_CRM_MAILCHIMP_AUDIENCE` |
| `FORM_FILE_SECRET` | secret | File upload fields (1.7): signs the one-time download links (16+ random characters). Without it (or without the `MEDIA` R2 binding) forms refuse files and ask the visitor to email them |
| `FORM_UPLOAD_DAYS` | var | Days a sent file and its link are kept (1–90; default `FORM_OUTBOX_DAYS`, else 30) |

Without working email (no `EMAIL_API_KEY`, or with `emdash` no provider selected in Settings → Email, or no
recipients) and without `FORM_OUTBOX` the endpoint answers 503 ("not available") rather than accept a message it cannot
deliver; with `FORM_OUTBOX` the message is kept and the cron emails it once email works.

**Keep sent — a full inbox (`FORM_OUTBOX_KEEP_SENT="1"`, kit.config `forms.outbox.keepSent: true`).** Without it the
outbox holds only messages that could not be emailed, so Form messages can show "Messages, 30 days: 1" under Insights
next to an empty Inbox. With it, every accepted message is stored (the same record as an outbox message, signature
included) with a delivery status:

| Status | When | Then |
|---|---|---|
| `emailed` | the provider accepted it (`emailedAt`, `emailedTo`, `messageId` when the provider returns one: Brevo, Resend, Postmark, Mailgun from the response body, SendGrid from `X-Message-Id`; none for `emdash`) | kept until the retention period ends; the cron never sends it again |
| `waiting` | not tried yet: email on hold or not set up | the cron sends it once email works → `emailed` |
| `failed` | the provider refused it (`attempts` counted) | the cron retries every 5 minutes → `emailed` |

Without keep sent the cron deletes a message once emailed, exactly as before. Either way every record — emailed or not —
is deleted when the retention period (`FORM_OUTBOX_DAYS`) ends: by KV's expiry, and by the cron, which also applies a
shortened period to messages stored earlier. Records written before 1.4 have no status and count as waiting (or failed
after a failed attempt). Saving an emailed message is best effort: if KV fails after the provider accepted it, the
visitor still gets "sent".

On Form messages the inbox then lists the newest 1,000 messages with an **Email** badge and an **Email** filter
(All / Waiting / Emailed / Failed) next to the read filter; the cards show In inbox, Waiting, Unread and Kept for. A
message page shows when it was emailed and to whom (admins already see the message; logs carry only a recipient count)
and the provider's message id. **Email it now** sends a waiting or failed message; **Email again** re-sends an emailed
one (or one imported for reference) after a confirmation, to the current recipients, and updates when and to whom.
**Email all now** sends only waiting and failed messages. Exports carry "Email status" and "Emailed at" (CSV) /
`emailStatus` and `emailedAt` (JSON), never the recipients; an import keeps `emailed` (so it is never sent again by the
cron) and brings any other status in as waiting. The dashboard widget lists the five newest messages.

**Recipients in the admin.** Plugins → Form messages → **Settings** (admins only, like the rest of the page): up to 10
addresses, one per line, checked before saving. They are stored in the outbox's KV (`cfg:recipients`), so the endpoint
reads them on every message, and the cron and "Email it now" use them too. Order: this setting, else `FORM_TO`. Saving
an empty list goes back to `FORM_TO`. The activity log records who changed them and how many addresses — never the
addresses. Needs `FORM_OUTBOX` (without it, recipients come from `FORM_TO` only).

**EmDash's email pipeline (`EMAIL_PROVIDER=emdash`).** The message goes through whatever the admin set up in EmDash
under Settings → Email — the built-in SMTP provider (needs `EMDASH_ENCRYPTION_KEY` to store its password), the
`EMAIL_SMTP_*` vars, or an email provider plugin — with the sender configured there. EmDash 1.5 does not give an
anonymous request to a site route `locals.emdash.email`, so the endpoint reaches the pipeline through
`withEmDashRuntime()` from `emdash/middleware` (server-only, the same call EmDash's own Worker and AI Search endpoint
use); the cron does the same. The message has one `to` (the first recipient) and the others as `cc`; reply-to is the
visitor's address. When no provider is selected the message is kept in the outbox (or the endpoint answers 503 without
one). EmDash's `email:beforeSend`/`email:afterSend` hook plugins see these messages with source `site-forms`: on a site
with sensitive forms, do not install plugins that hook those events. Turnstile test keys (always pass): site `1x00000000000000000000AA`, secret
`1x0000000000000000000000000000000AA` — for staging and `.dev.vars` only.

## Chat notifications

A new form message can also notify a chat app, with a link straight to the message in Form messages. Needs
`FORM_OUTBOX` (the settings live in its KV) and the cron line `ctx.waitUntil(flushChat(env).catch(() => {}))` next to
`flushOutbox` (import from `@wp2emdash/forms/chat`; the kit's starter has it).

**On by default, silent by default.** The section is always in **Form messages → Settings → Chat notifications** (admins
only), but nothing is sent until an admin turns a channel on **and** the channel's secret exists. A channel whose secret
is missing is not offered; the page says which secret to set (`wrangler secret put …`). `FORM_CHAT="0"` (kit.config
`forms.chat: false`) removes the feature.

| Channel | Secret (Worker secret, never in KV, code or logs) | Admin setting |
|---|---|---|
| Telegram (Bot API `sendMessage`, `parse_mode` HTML) | `TELEGRAM_BOT_TOKEN` | on/off, **chat id** (not a secret) |
| Slack (incoming webhook, mrkdwn) | `SLACK_WEBHOOK_URL` | on/off |
| Webhook (JSON POST) | `CHAT_WEBHOOK_URL` | on/off, format: JSON event · `{ text }` · Discord |

Also per site: **which forms notify** (all, or the ones ticked — the list comes from `formsPlugin({ forms })`, which the
kit's scaffold fills in, plus any form seen in the inbox) and **what is sent**:

| Mode | Contents |
|---|---|
| **Summary** (default) | form name, time (UTC), the sender's name when the form has a name field, the first ~200 characters of the message box (the form's first multi-line field), the link |
| **Notification only** | form name, time, the link — nothing the visitor wrote |

Never sent in either mode: email addresses, phone numbers, other fields, signatures, uploaded files or their links. On a
site with sensitive data (`FORM_SENSITIVE="1"`, kit.config `sensitiveData`) or for a form marked `sensitive`, only
**notification only** is possible, whatever was saved: the visitor's text never leaves the site. Visitor text is cleaned
(control characters and bidirectional overrides stripped, blank lines collapsed), cut to length and escaped per channel:
Telegram HTML (`&`, `<`, `>`), Slack mrkdwn (`&`, `<`, `>` — so no injected links or `<!channel>` mentions), Discord
markdown (backslash-escaped; `allowed_mentions: { parse: [] }`, so a visitor's `@everyone` does not ping). Link previews
are off on Telegram and Slack.

The link opens the message itself (`/_emdash/admin/plugins/site-forms/messages/<time>_<id>`; the page marks it read)
when the message is kept in Form messages — always with keep sent, or when email failed. Without keep sent an emailed
message is not kept: the notification says so and links to Form messages.

**Delivery never blocks the form.** The endpoint answers the visitor first; the notification runs in the Worker's
`waitUntil` (`import { waitUntil } from "cloudflare:workers"`), and `notifyChat` never throws. A channel that fails
(error, non-2xx, 8 s timeout, a redirect) becomes a small retry job in the same KV (`chat:<time>:<id>`, kept at most a
day; in summary mode it holds the name and excerpt for that time) and the 5-minute cron retries it — 5 attempts in all,
then it is dropped quietly and counted per day and channel (`chatfail:<day>:<channel>`, 30 days). Settings shows the
give-ups of the last 7 days, and **Site health**'s Forms check turns to a warning with a line when there are any.
A channel turned off (or whose secret was removed) meanwhile is dropped from pending retries; switching to
notification only also strips the name and excerpt from pending retries. Test messages (`FORM_LIVE_HOST`, sent from
workers.dev or a preview link) never notify.

**Send a test notification** (Settings, shown once a channel is on) sends a short test without visitor data to every
channel that is on; at most once a minute per site. Logs and the activity log record channel names and counts only —
never a token, webhook URL, chat id or anything a visitor wrote.

### Telegram

1. In Telegram, talk to **@BotFather** → `/newbot` → copy the token (`123456789:AA…`).
2. `npx wrangler secret put TELEGRAM_BOT_TOKEN` and paste it (per environment).
3. Add the bot to the group or channel that should get the messages (for a channel: as an admin who can post), or send
   the bot any message in a private chat.
4. Find the **chat id**: send a message in that chat, then open
   `https://api.telegram.org/bot<token>/getUpdates` in a browser (on your own machine — never paste the token anywhere
   else) and read `"chat":{"id": …}`. Private chats are a positive number, groups negative, channels start with `-100`.
   A public channel can also use its `@name`.
5. Form messages → Settings → Chat notifications: turn Telegram on, paste the chat id, save, **Send a test notification**.

### Slack

1. Create a Slack app (api.slack.com/apps → *From scratch*) → **Incoming Webhooks** → on → *Add New Webhook to
   Workspace* → choose the channel → copy the URL (`https://hooks.slack.com/services/…`).
2. `npx wrangler secret put SLACK_WEBHOOK_URL` and paste it.
3. Turn Slack on in Settings, save, send a test.

### Generic webhook (Discord, Google Chat, Teams, Make, Zapier, n8n)

`npx wrangler secret put CHAT_WEBHOOK_URL` with an `https://` address, then choose the format in Settings:

- **JSON event** (default) — for automation tools (Make, Zapier "Catch Hook", n8n Webhook node, Pipedream) and Microsoft
  Teams *Workflows* ("When a Teams webhook request is received"):

  ```json
  {
    "event": "form_message",
    "text": "New form message: Contact\nReceived: 2026-11-21 10:05 UTC\nFrom: Sam\nPlease call me back…\nOpen the message: https://example.com/_emdash/admin/plugins/site-forms/messages/2026-11-21T10_05_00.000Z_ab12cd34",
    "site": "example.com",
    "form": { "id": "contact", "title": "Contact" },
    "receivedAt": "2026-11-21T10:05:00.000Z",
    "link": "https://example.com/_emdash/admin/plugins/site-forms/messages/2026-11-21T10_05_00.000Z_ab12cd34",
    "content": "summary",
    "name": "Sam",
    "excerpt": "Please call me back…",
    "kept": true
  }
  ```

  In notification-only mode `name` and `excerpt` are absent and `content` is `"notice"`. The test button sends
  `"event": "test"`.
- **Text only** — `{ "text": "…" }`: Google Chat (space → Apps & integrations → Webhooks), Mattermost, Rocket.Chat and
  other Slack-compatible incoming webhooks. Google Chat rejects unknown fields, so do not use the JSON event there.
- **Discord** — `{ "content": "…", "allowed_mentions": { "parse": [] } }`: channel → Edit → Integrations → Webhooks →
  copy the URL.

### WhatsApp

There is no free, official way to post to WhatsApp without a **Meta Business** account: the WhatsApp Business
Platform (Cloud API) needs a Meta business, a verified phone number and approved message templates for messages a
business starts, and charges per conversation; Twilio's WhatsApp API sits on the same platform. So the package has no
native WhatsApp channel — use the generic webhook with an automation tool that holds those credentials:

1. In Make, Zapier or n8n, create a scenario that starts with a webhook (copy its URL into `CHAT_WEBHOOK_URL`, format
   *JSON event*).
2. Add a WhatsApp step — Make's / n8n's *WhatsApp Business Cloud* module or Zapier's *WhatsApp Notifications*, or a
   *Twilio → Send WhatsApp message* step — and map `text` (or `form.title` and `link` into an approved template).
3. Send a test notification from Settings.

The WhatsApp credentials then live in that tool, not in the site. On a sensitive site the payload is notification only
anyway; still, mind where the tool stores its run history.

## CRM and mailing lists (1.11)

A new form message can also create or update a contact in **Brevo**, **HubSpot** or **Mailchimp** — in addition to the
email, never instead of it. Needs `FORM_OUTBOX` (settings and retries live in its KV) and the cron line
`ctx.waitUntil(flushCrm(env).catch(() => {}))` (import from `@wp2emdash/forms/crm`; the kit's starter has it). Request
shapes, auth and the live checks still open: `docs/spikes/forms-crm-findings.md` in the kit.

**Present by default, silent by default.** **Form messages → Settings → CRM & mailing lists** (admins only) offers a
provider only once its Worker secret exists, and sends nothing until an admin turns it on and picks it for a form.
`FORM_CRM="0"` (kit.config `forms.crm: false`) removes the feature; kit.config `forms.crm.providers` pre-selects
providers for every form (auto-mapped) until an admin saves (`FORM_CRM_PRESELECT`, with `FORM_CRM_BREVO_LIST` /
`FORM_CRM_MAILCHIMP_AUDIENCE` — ids, not secrets). Empty by default.

| Provider | Worker secret | Call | Admin setting |
|---|---|---|---|
| Brevo | `BREVO_API_KEY`; without it, the email key `EMAIL_API_KEY` when `EMAIL_PROVIDER=brevo` | `POST api.brevo.com/v3/contacts` (`updateEnabled: true`) | on/off, list id for opt-ins, attribute names |
| HubSpot | `HUBSPOT_TOKEN` — a private app token with only `crm.objects.contacts.write` | `POST /crm/v3/objects/contacts`; on 409 `PATCH …/contacts/<email>?idProperty=email` | on/off, property names, opt-in property |
| Mailchimp | `MAILCHIMP_API_KEY` (its `-us21` ending is the data center; `MAILCHIMP_SERVER_PREFIX` overrides) | `PUT <dc>.api.mailchimp.com/3.0/lists/<audience>/members/<md5(email)>` | on/off, audience id, double opt-in, what to do without opt-in, merge tags |

**Per form**: which providers, and which form field is sent as email, first name, last name, full name (split at the
first space when no first / last name is mapped), phone, company, message, and the marketing opt-in checkbox. The
mapping is guessed from field names, labels and autocomplete hints (`your-email` → email, `newsletter` → opt-in; a
terms or privacy checkbox is never taken for an opt-in) and can be changed. **Only mapped fields are sent** — never the
rest of the submission, files, signatures or hidden fields. Provider-side names default to Brevo `FIRSTNAME`,
`LASTNAME`, `SMS` (sent only as an international number, `+…`), HubSpot `firstname`, `lastname`, `phone`, `company`,
`message`, Mailchimp `FNAME`, `LNAME`, `PHONE`; an empty name means "not sent to this provider" (Brevo and Mailchimp
have no company or message field unless you add one).

**Marketing consent.**

| | Opt-in mapped and ticked | Not ticked, or no opt-in field |
|---|---|---|
| Brevo | contact created/updated **and added to the list** | contact created/updated, no list |
| HubSpot | contact created/updated, the opt-in property (if named) set to `true` | contact created/updated only |
| Mailchimp | `subscribed` (`pending` with double opt-in, the default) — also re-subscribes an existing member | skipped (default), or `status_if_new: "transactional"` — an existing member keeps its status |

An existing contact's subscription is never changed without a tick. HubSpot's marketing subscription itself
(communication preferences) is not touched: it needs a broader scope; use the opt-in property in a HubSpot workflow.

**Sensitive data: impossible.** On a site with `FORM_SENSITIVE="1"` (kit.config `sensitiveData`) or for a form marked
`sensitive`, the section shows why it is unavailable, saving refuses it (also for a crafted request), a new message is
never synced and pending retries are dropped. Test messages (`FORM_LIVE_HOST`) and the opt-in staging environment
(`STAGING="1"`) never sync either.

**Delivery never blocks the form.** The sync runs in `waitUntil` beside the chat notification. A temporary failure
(network, timeout, 408, 425, 429, 5xx) becomes a retry job in the same KV (`crm:<time>:<id>`: the mapped contact only,
kept two days at most) retried by the cron after 5 min, 15 min, 1 h, 4 h and 12 h (6 attempts). A permanent error
(401, 403, 400 …) or the last attempt is counted per day and provider (`crmfail:`, 30 days) and the provider's error
text — with the contact's values, any email address and long numbers removed — kept as that provider's last error
(`crmerr:<provider>`), shown in Settings with a Clear button. Logs carry provider names and counts only.

## File uploads (1.7)

A `file` field's files are checked after Turnstile and validation (extension, size, the first bytes: a `.pdf` must start
with `%PDF`, a `.docx` is a ZIP…; the stored content type comes from the extension table, never the browser), then stored
in the site's R2 bucket (`MEDIA`) under `backups/form-uploads/<form>/<day>/<random>/<name>` — EmDash's public media route
never serves `backups/`. The email gets one line per file: name, size and a link
`/api/forms/file?k=…&e=…&s=…` (HMAC-SHA256 with `FORM_FILE_SECRET`). Opening it shows a Download button; the download
(a POST) works once, then the link answers 410 (`<key>.used` marks it). Serve the route from
`src/pages/api/forms/file.ts`:

```ts
import { env } from "cloudflare:workers";
import { createDownloadHandlers, type UploadEnv } from "@wp2emdash/forms/uploads";
export const prerender = false;
const h = createDownloadHandlers(() => env as unknown as UploadEnv);
export const GET = h.GET;
export const POST = h.POST;
```

and call `purgeUploads(env)` from the Worker's cron (the kit's starter does it hourly on sites with file fields): files
older than `FORM_UPLOAD_DAYS` are deleted. Sites with sensitive data get no file fields unless the owner allowed them
(the kit's `forms.uploads.sensitive`). File names and contents never reach logs.

## Signatures, consent and the emailed record

**The pad** (`@wp2emdash/forms/signature-pad`, `mountSignaturePads()`, no dependencies; markup in its header and in the
kit starter's `Form.astro`): draw with mouse, finger or pen (pointer events), **Clear signature** button. After each
stroke the drawing is cropped to the strokes, scaled to fit 600×200 on white and written to a hidden input as a PNG
data URL (kept under 150 KB). The canvas is skipped by the keyboard: its label tells keyboard and screen-reader users
to type their full name in the input below it, which is always there (and is the whole field without JavaScript — the
pad stays hidden). A drawing or a typed name satisfies a required signature.

**The endpoint** accepts a drawing only if it is `data:image/png;base64,`, at most 150 KB (checked from the length
before decoding), decodes, starts with the PNG signature bytes and an IHDR chunk, and is at most 600×200; a typed name
is 2–200 characters with a letter and no markup. A refused signature is a 422 on the field. Signatures are never
logged (logs carry the form id, outcome and a reason word).

**The email** is a complete record: form title, submission time (UTC), every answer, consent as
`Accepted: "<the consent text>"`, and — for a form with consent, `content` or a signature — the exact text shown on
the form (terms, consent label with link targets) and its SHA-256, so the record can be checked against the form
later. A drawn signature is sent as an attachment, `signature.png`:

| `EMAIL_PROVIDER` | Signature |
|---|---|
| brevo | attachment (`attachment[{ name, content }]`) |
| resend | attachment (`attachments[{ filename, content }]`) |
| postmark | attachment (`Attachments[{ Name, Content, ContentType }]`) |
| sendgrid | attachment (`attachments[{ content, filename, type, disposition }]`) |
| mailgun | attachment (multipart `attachment` part) |
| emdash | **embedded** in the HTML part as a data-URI image: EmDash 1.5's email message has no attachments. Gmail and some Outlook versions do not show data-URI images — use an API provider for signed forms |

**The outbox** keeps the message with its signature (as base64, in KV) until it is emailed or the retention period
ends, like any message (with keep sent, until the retention period ends, emailed or not); the cron sends it with the attachment. On **Form messages** a message with a signature says
"signature attached" in the inbox and shows the image on the message page (admins only; only a stored PNG that passes
the same checks is shown). CSV/JSON exports carry the text record, not the image.

## AI agents (WebMCP)

`@wp2emdash/forms/webmcp` gives a form the WebMCP declarative attributes (`toolname`, `tooldescription`,
`toolparamdescription`), so an AI agent in Chrome can fill it in. Plain HTML, no script. Everything comes from the form
definition (id, title, labels, options, submit label). The agent fills the form; the visitor checks it and presses
Submit, so Turnstile and the honeypot work as before (the honeypot is described to agents as "leave empty"). Forms
marked `sensitive` and every form on a site with `FORM_SENSITIVE="1"` are not exposed. Off: `FORM_WEBMCP="0"`. Details
and what Lighthouse checks: kit `docs/spikes/webmcp-findings.md`.

```astro
---
import { formTool, paramDescription, HONEYPOT_DESCRIPTION } from "@wp2emdash/forms/webmcp";
const tool = formTool(form, env); // undefined: not exposed
---
<form {...(tool ?? {})}>
  <input name={f.name} toolparamdescription={paramDescription(f, form, env)} />
```

## Privacy

- The endpoint reads only the form's own fields and stores nothing unless the outbox is on — then only until the
  message is emailed or the retention period ends.
- **Keep sent is a data-retention decision.** With it, what visitors wrote stays in Workers KV for the whole retention
  period even after it was emailed — a second copy beside the recipients' mailboxes, readable by every site Admin and
  by anyone with access to the Cloudflare account. Record the owner's choice (kit `decisions.md`) and say so in the
  site's privacy policy. For sites handling health, legal or financial data, leave it off unless the owner explicitly
  wants an inbox, and then keep the retention period short.
- With the outbox, one count per day, outcome (emailed / kept) and form is kept for 400 days for the charts: no names,
  addresses or text.
- The admin page is for the **Admin** role only: EmDash enforces `plugins:manage` and its CSRF header before the
  handler runs, and the handler checks the role again. Other roles see "Admins only" (the menu item is visible to them
  in EmDash 1.5; plugin pages have no role filter there).
- Visitor text is shown as plain text. Exports go through a random link that works once, for two minutes, and are
  sent with `Content-Disposition: attachment` under EmDash's sandbox headers; CSV cells that look like formulas are
  neutralised. Imports rebuild the email body from the text (imported HTML is never used).
- The activity log (180 days) and logs record actions and counts, never message content or recipient addresses.
- **Chat notifications send data to a third party** (Telegram, Slack, the webhook's service). In summary mode that is the
  sender's name and the start of the message — the site admin's choice, worth a line in the privacy policy;
  notification only sends nothing a visitor wrote, and is the only mode on sites with sensitive data.
- **CRM sync sends the mapped fields to a third party** (Brevo, HubSpot, Mailchimp): the business's own account, but a
  processor to name in the privacy policy. Marketing subscription only with a ticked opt-in. Never on sites with
  sensitive data or for sensitive forms.
- For sites handling health, legal or financial data, keep forms to contact details only and tell visitors not to send
  sensitive details (`notice` on the form definition).
- **Signatures are personal data.** They are emailed to the recipients and, with the outbox, kept in KV only until
  emailed or for the retention period (`FORM_OUTBOX_DAYS`; with keep sent, for the whole period) — the site is not an archive of signed forms. The business
  should keep the signed emails (a waiver's signed copy) for as long as its own policy and local law require, in its
  own records, and delete them after that. The kit's contact-only policy for sensitive sites withholds radio, consent,
  content and signature fields like any other non-contact field; whether a sensitive site may collect signatures is
  the owner's decision (kit.config `forms.sensitive`).
