## [1.9.0] — 2026-11-22

### Added
- **`wp2emdash sync-staging <slug> [--yes] [--no-media] [--json]`** (sites with staging only): refreshes staging with production's content so upgrades are checked on real content. Strictly production → staging. Production is only read — SELECT / PRAGMA statements over D1's REST query endpoint (the call `wrangler d1 execute --remote --command` makes; every statement passes a read-only guard) and R2 object GETs; not `wrangler d1 export`, which makes the database unavailable while it runs (Wrangler 4.163.0). An explicit table allowlist classified against EmDash 1.5's migrations (001_initial … 097_room_storage): content tables, revisions, media records, media folders, taxonomies, menus, widgets, sections, bylines (their link to a user account written as NULL), SEO rows, redirects, collection / field / section-type definitions, site settings (staging keeps its own `site:url` and `site:staging`) and allowlisted kit plugin configuration (cookie banner, motion, sharing-card design, SEO panel rows, business switch). Never copied: users, passkeys, sign-in and API tokens, OAuth clients, plugin storage (form messages), form recipients / CRM / chat settings, change requests, the sharing-card secret, analytics settings, comments, logs, runtime state, the schema version — every left-out table is listed in the plan with the reason. Refuses a site without staging, a staging database that is production's (or its restore-test database), shared D1 names and shared R2 buckets, and a staging schema behind production's. Dry run by default (plan: row counts per table on both sides, media files); `--yes` takes a D1 Time Travel bookmark of staging first (refused without one; recorded in `sync/d1-bookmarks.jsonl` with the restore command), copies media files bucket to bucket (missing or different size only; backups and transfers never), imports the rows with one atomic `wrangler d1 execute <staging> --remote --file` addressed by staging's recorded database id through a temporary one-binding config, reads the counts back, and purges staging's cached pages with an unchanged settings save through its EmDash API (`EMDASH_TOKEN`). Logs and results hold counts and table names only; the SQL file lives in a temp directory and is deleted after the import. Findings: `docs/spikes/staging-sync-findings.md`.
- **`wp2emdash upgrade <slug> --deploy-staging --sync-staging [--yes]`**: the sync runs first, before any snapshot, so the staging before/after comparison runs on production's content. Without `--yes` upgrade prints the sync plan and stops (exit 1) before snapshotting, rebuilding or deploying anything; with it, the sync is applied, upgrade waits 35 s (isolates keep settings 30 s), then continues as before.
- **Accessibility** (Site health → Accessibility, `@wp2emdash/health` 0.8.0, on by default; kit.config `health.accessibility: false` turns it off): with the weekly visual check, the HTML it already fetched is checked for common problems — no extra request, no browser. Rules named as axe names them (the tool the kit's verify uses): pictures without an alt attribute (`alt=""` is decorative and fine) or with the file name as alt, no / several `<h1>`, heading levels skipped (two or more down), links and buttons without an accessible name (text, aria-label, aria-labelledby, title, picture alt, SVG title), empty links, form fields without a label (label[for], wrapping label, aria-label/-labelledby, title, placeholder), duplicate ids (not inside inline SVG icons), `<html>` without `lang`, iframes without a title. aria-hidden, `hidden`, `<template>`, `<noscript>` and the comments section are skipped, so the starter's decorative markup never shows. The same issue on several pages (a footer link on every page) is one item; each says what it is, why it matters and how to fix it in the admin, with **Edit the page** when it concerns one page.
- **Content freshness** (Site health → Content freshness, on by default; kit.config `health.freshness: false`, `health.staleMonths`, default 18, 0 = never): past event dates in page text (a full date with its weekday, or full / numeric / month-year dates next to an event word; history after "since", "founded", "posted", "updated" skipped; numeric dates only when past read either way and never with dashes, so phone numbers and prices do not match; English plus German, French, Spanish and Dutch month names), ended year-bound phrases ("Summer 2023", "Black Friday 2024", "2024 offer", "© 2023"; the kit's own footer credit is always the current year), and pages not saved for 18 months. Pages only — posts are left out — and legal (privacy, terms, cookies, imprint, refund, …) and thank-you pages are skipped by slug. Text from the visual check's HTML plus one `ctx.content.list` pass over the pages at the end of the run.
- Both feed **What to improve** (and so the monthly report): accessibility issues on many pages rank above single-page ones; past dates in the middle; old pages low. Items link to Site health's tabs, or to the page's editor (`/_emdash/admin/content/<collection>/<id>`, the EmDash 1.5 admin route) when they concern one page. Admins can **Dismiss** an item for 3 months, a year or for good ("this date is a historic fact"; KV `review:dismissed`, ≤ 200, expired ones dropped) and show it again. No email alerts for these (weekly noise). Stored in KV `review` (≤ 60 items per part, short strings, never visitor data). Findings: `docs/spikes/health-findings.md` ("Accessibility and content freshness").
- **WordPress end-to-end test** ([docs/e2e.md](docs/e2e.md)): a throwaway WordPress in Docker (`e2e/wordpress/docker-compose.yml`, images pinned) with Elementor 4.4.1, WooCommerce 11.3.1, Polylang 3.9.2, Contact Form 7 6.2.5, Fluent Forms 6.2.17, the EmDash Exporter 1.2.0 and Twenty Twenty-One, each pinned by version and sha256 (`e2e/lib/versions.ts`). A deterministic synthetic site (`e2e/lib/plan.ts`: 10 Elementor and Gutenberg pages, 7 posts, menus, 6 simple and variable products, a Fluent Forms and a CF7 form, English + French under `/fr/` with translated pairs, locally generated PNGs) is seeded with WP-CLI (`seed-languages.php`, `seed.php`), then `e2e/run.sh` runs the kit in a temporary sites folder — init → audit → extract → transform → scaffold, then load and verify against the generated project's local dev server — and checks the output beyond the gates (products collection and variations, Elementor pages without unmapped content, both form plugins mapped, Polylang groups and prefixes, rendered `hreflang` and language switcher). Failed gates never stop the run (later phases run as `--preview`) and are never accepted; `e2e/expectations.json` holds required phases and dated known failures. Report (`report.md` as the job summary, `report.json`, logs, kit reports, IR, rendered pages; credentials scrubbed) uploaded as an artifact. GitHub Actions workflow `E2E WordPress`: Run workflow and nightly, never on push; read-only token, no secrets, no Cloudflare variables (the runner refuses them), Cloudflare's API blackholed. Unit tests for the plan, the PHP/TS contract, the Elementor adapter on the seeded trees, pins, the workflow's guarantees, the runner loop, verdict, assertions and report (`test/e2e-wordpress.test.ts`).

### Changed
- SEO fix-it: no focus keyword is drafted for legal pages (privacy, terms, cookies, waivers…) — found on the first live run; a description still is.

### Fixed
- **Every translated page answered 404 on multilingual sites:** the blog's category/tag/author base was read from term links, and translated terms (`/fr/category/…`) could make it `/fr/`, so every French address was taken for an archive. Bases now ignore language directories. Found by the WordPress end-to-end test; verified on EmDash 1.5 that nested slugs like `fr/a-propos` resolve normally.
- Animated counters (Elementor) are read at their end number by text conservation, as the visitor sees them.
- **Gutenberg quotes lost their text:** in WordPress 6.x a quote (and pullquote) holds its paragraphs as inner blocks; the adapter kept only the citation. The block parser now records where inner blocks sit (`innerContent`, as WordPress's own parser) and prose blocks are rebuilt in full; row fingerprints are unchanged. Fixture `gutenberg/quote-inner-blocks`. Found by the WordPress end-to-end test.
- Text conservation counts form choices stored as a plain list (Contact Form 7 `[select]` options) and product prices as the shop prints them (`$28.00`), and leaves out WooCommerce's sale badge and tab headings.
- **Multilingual sites could not be set up:** the kit's language-group field was named `translation_group`, a system column on every EmDash 1.5 content table — the seed failed with "duplicate column name". It is now `lang_group` (no delivered site used it). Found by the WordPress end-to-end test.
- WordPress's comment form (and WooCommerce's review form) is recognised and left out like the search form; the comments feature imports comments with its own form.
- Text conservation ignores the WooCommerce template parts catalogue mode does not carry (related products, reviews tab, tab labels, breadcrumbs, add-to-cart box, stock and sorting notes) and the comment form; product names, prices, descriptions and attributes are still compared.
- **New projects could not build:** `@astrojs/cloudflare` accepts any newer `@cloudflare/vite-plugin`, and 1.70.1 needs Wrangler ≥ 4.164 while the kit pins 4.163.0; a project without a lockfile picked it up. The starter's `pnpm-workspace.yaml` now pins the plugin (1.70.0, `STACK`). Sites with a lockfile were not affected.
- **The audit no longer requests addresses that make WordPress do something:** `?add-to-cart=`, cart removals, comment replies, logins, nonce'd actions and admin/xmlrpc paths are never crawled, link-checked or sampled (`isActionUrl`; an add-to-cart request creates a cart session in the live site's database). Also in `estimate`.
- WooCommerce's own forms (add to cart, variations, sorting, cart, checkout, account, product search) are recognised and left out like the search form — catalogue mode's Buy button replaces them — instead of counting as unknown live forms in the extract `forms` gate.
- WooCommerce variation templates, its no-JS class swap and Elementor's background lazy-load script are classified as WordPress code (not needed) instead of site-wide snippets needing a decision.
- Extract `languages` gate on Polylang/WPML sites no longer asks for a language on entries without an address: WooCommerce variations (they follow their product) and post types WordPress does not list as viewable (Contact Form 7 form definitions, plugin internals) — `languageChecked` in `src/transform/multilingual.ts`.

## [1.8.0] — 2026-11-22

### Added
- **SEO fix-it** (`@wp2emdash/seo` 0.6.0, SEO & Analytics → **SEO fix-it**, editors and admins): drafts the missing meta descriptions (120–160 characters) and focus keywords (2–4 words found in the page text), and optionally SEO titles that are too long or short (≤ 60), with Workers AI (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`, JSON mode, the site's language) from each published, indexable page's own title and visible text. Drafts are validated and cleaned (plain text; phone numbers, prices, emails and links not on the page removed; unsupported claims removed or flagged). Review table per page: current vs suggested values, editable, **Approve** / **Discard**, **Approve all shown**. Approval writes the SEO fields with `content.update(…, { seo })` (new capability `content:write`, SEO fields only) — not versioned, so live at once on a published page, as the page says — and the keyword to the panel's KV, refuses values changed since the draft, then purges the cached pages. 10 pages per press, 100 drafts per UTC day by default (about half the free daily neurons). Pending suggestions in plugin KV (≤ 200, 30 days, never the page text). Without the AI binding the page explains how to add it. Options `fixit: { model, dailyLimit, titles }` or `fixit: false`. Findings: `docs/spikes/seo-fixit-findings.md`.
- **Scaffold:** the Worker gets the Workers AI binding when the SEO panel is on (as before also with Media AI alt text), except on `sensitiveData` sites.

### Changed
- Site health 0.7.0: the "What to improve" item for missing search descriptions opens SEO fix-it (needs `@wp2emdash/seo` ≥ 0.6).
- **`wp2emdash estimate <url>`**: a sales estimate for a prospect's public WordPress site, without login, `init` or a site workspace. Reads the site politely (GET/HEAD only, robots.txt and Crawl-delay respected, generic user agent, ≤ 4 requests at a time, ≤ 300 addresses collected, ≤ 25 pages read; REST totals instead of listings) and reuses the audit's discovery, fingerprint, integrations scan and WooCommerce Store API reader. Speed without a browser (TTFB, page weight, requests, image formats for the home page and two more) compared with the kit's measured numbers and verify gates; `--lab` adds PageSpeed Insights (PAGESPEED_API_KEY / CRUX_API_KEY), CrUX field data with CRUX_API_KEY. Findings mapped to the kit's real scope: out of scope (PLAN §9, not estimated), owner decisions (shop catalogue mode, sensitive forms, languages on other hosts), adapters proven on real sites vs fixture-only. Transparent hours range from rules in `src/estimate/rules.ts` (`--rules <file.json>` to tune), `--rate` for an amount. Writes `estimates/<host>-<date>/` (gitignored): `report.html` (client-facing, printable, agency-branded; `--agency`), `report.md`, `internal.md`, `estimate.json` (`--json`). Also in the wizard.
- Audit fingerprint knows more plugins: memberships, LMS and community plugins (MemberPress, Paid Memberships Pro, Restrict Content, LearnDash, LifterLMS, Tutor, Sensei, BuddyPress, bbPress, Ultimate Member, Profile Builder) are out of scope as PLAN §9 says; builders without an adapter (Beaver Builder, Oxygen, Breakdance, Brizy, Thrive, SiteOrigin, Avada) go to the DOM fallback; Gutenberg block libraries, Jetpack and a few common utility plugins are named.
- **Backup restore test** (`@wp2emdash/backups` 0.2.0, on by default; kit.config `backups.restoreDrill: { everyDays, mediaSample, tolerancePct }` or `false`): once a month the site proves its newest backup can actually be restored. The file is checked (SHA-256 of the stored gzip, now recorded in R2 custom metadata and the backup list when a backup is stored; decompression; format; its counts against its own rows and list entry), then restored into an **empty scratch D1 database** bound as `RESTORE_DRILL_DB`: each table created from the live schema (columns, types, NOT NULL, defaults, primary keys; no foreign keys), every row inserted in batches within D1's 100-bound-values limit, every table counted back against the backup (exact by default), pages / posts per collection, media records and site settings checked, a sample of media files checked in R2 (HEAD, same size), privacy re-checked (no excluded tables or disallowed settings rows — counted, never read out), then the scratch database emptied. Without the binding (sites not yet provisioned) it runs as a **dry run** against the live schema and writes nothing. The scratch database is written only when it is empty or holds the test's own marker table — never the live `DB` binding. Plugin cron task `restore-drill` every 15 minutes at site-fixed minutes, ≤ 400 statements / 60 s per tick with progress in plugin KV, its own lock, never on staging; a failed test is retried the next day. Backups page: "Last restore test: passed 2026-11-03, 1,234 rows across 38 tables, 12 media sampled", failed checks listed, **Run restore test now** (admins, at most every 10 minutes); the private `status` route carries it; a failure emails the backup alert recipients once, a pass afterwards sends a recovery email. Counts, table names and dates only — never content.
- `wp2emdash provision` creates the empty `<slug>-restore-drill-db` D1 database for production (not staging; skipped with `backups: false` or `restoreDrill: false`) and records it as `production.restoreDrill` in `cloudflare.json`; the scaffold binds it as `RESTORE_DRILL_DB` only once its id is recorded (a binding without an id would be auto-provisioned by `wrangler deploy`), so existing sites keep building unchanged and run the dry run until then. Client repo docs explain the test.
- Site health (`@wp2emdash/health` 0.7.0): the Backups check also reads the last restore test (one SELECT of `plugin:site-backups:drill`): a failed test turns an otherwise good check into a warning; the result is a detail line, with a note after 45 days without a test. Findings: `docs/spikes/backup-findings.md` ("Restore test").

## [1.7.0] — 2026-11-22

### Added
- **`wp2emdash fleet`**: one view of every site for an agency with many deliveries. Per site: environments (production on its live domain or workers.dev address, opt-in staging), the kit version the project was built with against the current kit ("behind by 2 minor versions"), every `@wp2emdash/*` package in the project's `packages/` against the kit's, the client project's last commit, the latest upgrade snapshot (`reports/upgrade/<timestamp>/`) and its comparison results, and owner to-dos from structured sources only (failed gates not accepted, the next gate, proposals waiting for approval, open ACCESS.md items, an upgrade not verified on production, the monitoring window after go-live). Compact terminal table or `--json`; `--sites a,b`. `--live` (read-only): GET of the home page (status, response time) and the last production deploy from `wrangler deployments list --json`, run in the project with the site's credentials as `provision` resolves them (tokens never printed; author addresses left out). Dashboard: a **Fleet** page in `wp2emdash ui` (`/api/fleet`, local files only).
- **Build marker** `.wp2emdash.json`: the scaffold now writes the kit version, build time and package versions at the client project root, so a delivered project says which kit built it. Projects built before it show "unknown" until their next rebuild (package versions are still read from `packages/*/package.json`).
- **`wp2emdash fleet upgrade-prs`**: for every site behind the kit, a `wp2emdash/v<version>` branch in its client project with the scaffold rebuilt on it (like `upgrade`, preview-style when earlier gates are not recorded) and committed, then the `gh pr create` command. Dry run by default; `--apply` creates the branch and commits locally (then switches back to main); `--open` also pushes the branch (explicit refspec, never main) and opens the pull request with `gh`. Refuses per site: no project folder or not its own git repository, not on main or detached, uncommitted changes, branch already present (locally or as a known origin branch), no origin (`--open`), and any `.github/workflows` file where a push of the branch or a pull request from it could run a deploy job — checked before branching and again after the rebuild (`src/upgrade/ci-safety.ts`: trigger filters, job `if:` conditions evaluated three-valued, unreadable workflows and reusable workflows count as unsafe). A failed scaffold gate removes the branch and leaves main as it was. The workflows the scaffold generates are tested to deploy only from main or Run workflow.
- **Form leads to a CRM or mailing list** (`@wp2emdash/forms` 1.11.0, `@wp2emdash/forms/crm`): besides the email, a new form message can create or update a contact in **Brevo** (contacts API, optional list for opt-ins), **HubSpot** (CRM v3 contacts: create, on 409 update by email — a private app token with only `crm.objects.contacts.write`) or **Mailchimp** (audience member upsert by MD5 hash). Form messages → Settings → **CRM & mailing lists**: a switch per provider, offered only once its Worker secret exists (`BREVO_API_KEY` — or the Brevo email key when `EMAIL_PROVIDER=brevo` —, `HUBSPOT_TOKEN`, `MAILCHIMP_API_KEY`), list / audience ids, editable provider field names, and per form which providers and which field is sent as email, first / last / full name, phone, company, message or the marketing opt-in (auto-mapped from field names; a terms checkbox is never an opt-in). Only mapped fields are sent. Marketing subscription only with a ticked opt-in (Brevo list, Mailchimp `subscribed` / `pending` with double opt-in, HubSpot opt-in property); otherwise a contact only (Mailchimp: skipped by default, or `transactional`), and an existing subscription is never changed. Runs in `waitUntil` after the visitor's answer; temporary failures retried by the 5-minute cron with backoff (5 min → 12 h, 6 attempts, jobs hold the mapped contact only, two days at most); permanent errors and give-ups counted and shown in Settings with the provider's error text scrubbed of personal data. Impossible on `sensitiveData` sites and for sensitive forms (shown as unavailable with the reason, refused when saving — also for crafted requests —, at send time and at retry time); never for test messages or on staging. kit.config `forms.crm`: `{ providers, brevoListId, mailchimpAudienceId }` pre-selects providers (empty by default), `false` removes the feature (`FORM_CRM="0"`). The plugin descriptor now carries each form's mappable fields and `sensitive` flag. Client repo docs (forms & integrations, deployment secrets), the dashboard's Environment and Secrets views list the optional secrets. Findings: `docs/spikes/forms-crm-findings.md`.
- **Outside-in monitor** (`wp2emdash monitor init|build`, `@wp2emdash/monitor` 0.1.0, [docs/monitor.md](docs/monitor.md)): Site health runs inside each site's Worker, so a broken Worker, account, DNS or domain alerted no one. The monitor is ONE Cloudflare Worker the agency deploys once (ideally in its own account, `accountId`) with a 5-minute cron: every deployed site's home page (its domain once `cloudflare.json` says `production.live`, else workers.dev) plus `extraUrls`, checked from outside with `global_fetch_strictly_public` — 2xx within 10 s, same-site redirects only, a `<title>`, no Cloudflare error / 52x / challenge page, optional keyword. Two failures in a row open an incident, the first good check closes it; one message per tick on email (the forms' providers, Brevo by default, `EMAIL_API_KEY` secret), Telegram and Slack, ≤ 20 a day, retried when no channel delivers. Daily certificate expiry from Certificate Transparency (Cert Spotter) and domain expiry from RDAP, warned at ≤ 14 days, spread over the day by slot. Weekly summary (off by default). Optional `HEARTBEAT_URL` dead-man's switch. State in one KV key written only on change plus a daily heartbeat (≤ 288 writes/day by construction, typically 1–3). Status page at the Worker's URL, 404 without `?token=<STATUS_TOKEN>`. Generated into `monitor/` (gitignored) or `--dir`; URLs and addresses only, secrets via `wrangler secret put`; the kit never deploys it. GitHub Actions schedules were rejected (delayed or dropped under load, disabled after 60 inactive days); crt.sh answered 502 throughout. Findings: `docs/spikes/monitor-findings.md`.

## [1.6.0] — 2026-11-22

### Added
- **`wp2emdash upgrade <slug>`**: moves an already-delivered site to the current kit version and proves visitors see the same site. Snapshots every page of the address the client is live on (sitemap; status, title, meta description, h1, `<html lang>`, hreflang count, visible-text hash and word count, link / image / form counts, stylesheets, scripts, font families) to `sites/<slug>/reports/upgrade/<timestamp>/before.json`, reruns the scaffold phase (a failed gate stops it), and on opt-in staging sites with `--deploy-staging` snapshots staging too, runs the project's `ci:deploy:staging` and compares staging after with staging before (same environment, so only what the upgrade changed shows). `--preview` rebuilds without requiring earlier gates or touching `state.json`, for sites delivered before the kit recorded every phase; without it, missing gates are reported before anything is fetched. Expected rebuild noise is ignored (asset hashes in file names, cache-busting query strings, copyright year, kit version, nonces); renamed bundles and new pages are reported as expected changes, a lost font or page is a difference. Production is never deployed: the exact command is printed for the owner, then `upgrade <slug> --verify` compares production with the saved snapshot (`--verify staging` or `--verify <url>`, e.g. a Workers version preview, too). Markdown + JSON report per comparison; exit 0 identical · 2 differences · 1 error; `--json`. MCP tool `upgrade_verify` (read-only comparison).
- **Visual check** (Site health → Visual check, `@wp2emdash/health` 0.6.0): once a week the plugin reads the home page and the sitemap's main pages (default 10; kit.config `health.visualPages`, 0–25, 0 = off) through the Worker itself and keeps a structural fingerprint — status, title, main heading, the starter's sections in order, pictures (each checked for 200 + image/*; EmDash `/_image` variants checked as their original file, so no Images transformations), stylesheets, `@font-face` / Google Fonts families, visible words, footer. The first run is the baseline; later runs report a page that errors, a picture, stylesheet or font that no longer loads, a missing footer or an empty page, and changes beyond tolerance (text ±30 %, fewer pictures, a section type gone, title or heading changed) — whatever caused them (deploy, admin edit, settings, outside services). One alert email through the normal alert path and a "What to improve" item; the tab explains each difference in plain words, with **Accept current as new baseline** (all pages or one, admins only) and **Check now**. A page saved in the editor since its baseline takes its new look automatically unless something is broken (EmDash content `updatedAt`). Runs resumably in the existing 5-minute cron (≤ 8 requests a tick, never in the PageSpeed test's tick), keeps the last 8 runs in plugin KV, not on staging, paused in coming-soon mode. No screenshots: Cloudflare Browser Rendering would need a new binding (not added). Findings: `docs/spikes/health-findings.md`.
- **Product grid section** (WooCommerce catalogue mode only; PLAN §8b, `docs/spikes/shop-findings.md`): editors can place a grid of products on any page ("Featured products" on the home page): heading, intro, which products (newest, on sale, product categories, hand-picked product addresses), how many (default 4, max 12), products per row, show price, button label (empty = the product's own Buy wording, else "View product"). It reuses the shop's product cards, reads the products server-side (cached pages, purged by the `products` tag) and adds an ItemList of the product pages (no duplicate Product JSON-LD). The transform maps WooCommerce blocks (hand-picked, product category, on sale, newest, Product Collection), the shortcodes `[products]`, `[featured_products]`, `[sale_products]`, `[recent_products]`, `[product_category]`, Salient's WooCommerce products element and Elementor Pro's Products widget; product ids become product addresses and WordPress's featured products a hand-picked list. Best sellers, top rated, attribute/tag filters, add-to-cart and single-product shortcodes are reported in the coverage report. Sites without a shop are unchanged: no new block type, allowed section, editor-guide entry or output (`test/product-grid-noshop.test.ts`); a grid found on such a site is reported, not kept. The editor guide explains the section on shop sites.

## [1.5.0] — 2026-11-22

### Added
- **Deploy check with automatic rollback** (`performance.deployCheck`, `performance.rollback`, both on): every deploy script runs `scripts/deploy-check.mjs` after the warm-up — sitemap pages answer, titles / main content / footer present, stylesheets, scripts and the hero picture load, every font the site uses is in its CSS. On a failure the Worker is rolled back to the version live before and the deploy fails. `DEPLOY_ROLLBACK=0` skips the rollback for one run.
- **What to improve this month** (`@wp2emdash/health` 0.5.0): the monthly report email (HTML and plain text) opens with at most six plain-language to-dos, most important first, each with the pages, addresses or pictures it concerns (three named, the rest counted) and a link to the admin page that fixes it; the Site health **Overview** shows the same list (Site health's own items open the Missing pages or Speed tab). Sources, all already stored: backups failing, broken / undescribed / oversized pictures (Media Assistant), slow real-visitor speed (CrUX), missing addresses without a redirect (404 log), form messages down by half (monthly counts only, no message read), thin pages, missing meta descriptions and focus keywords (SEO suite). Plugins a site does not run are skipped; nothing to do is one positive line. Stored reports from before show no section.
- **SEO summary for other plugins** (`@wp2emdash/seo` 0.5.0, `@wp2emdash/seo/summary`): the SEO dashboard and widget cache a small summary of their page analysis in KV `summary` (D1 `plugin:site-seo:summary`; counts and page titles; written only when changed or 6 hours old). Site health 0.4.0 needs `@wp2emdash/seo` ≥ 0.5.
- **Weekly lab score** (Site health → Speed, `@wp2emdash/health` 0.5.0): every 7 days Google PageSpeed Insights tests the home page on mobile and desktop (performance, accessibility, best practices, SEO); the tab shows the latest scores, FCP / LCP / TBT / CLS / Speed Index, the LCP element, a chart and the last 8 tests with ▲ / ▼ changes, and a plain-words line on lab vs real-visitor data. 26 weeks kept in plugin KV (≤ 80 runs). **Run PageSpeed test now** (admins, at most every 10 minutes) is picked up by the next cron tick, since a Lighthouse run outlasts an admin request's `waitUntil`. Key: new optional Worker secret `PAGESPEED_API_KEY`, or `CRUX_API_KEY` with the PageSpeed Insights API enabled on the same Google Cloud project; without a key nothing is called (Google's anonymous quota answers 429) and the tab shows the setup steps. Alert when the mobile performance score drops by 15 points or more. Findings: `docs/spikes/health-findings.md`.
- **WooCommerce catalogue mode** (PLAN §8b, `docs/spikes/shop-findings.md`): kit.config `shop: { mode: "catalogue", checkout: "external" | "stripe-payment-links" | "contact" }` lets a small shop migrate (owner decision; unset, the new audit/transform gate `shop` stops the site). - An inlined component script (the comment form, under Astro's 4 KB inline limit) was blocked by the public CSP on every page: generated projects never inline scripts (`vite.build.assetsInlineLimit: 0`) and the comment script renders only where the comment form does.
- Verify crashed before the old-address check (`archivePaths` used before it was defined).
- Verify's menu capture clicked the consent banner's button instead of the burger, and screenshots accepted the kit's own banner instead of rejecting it: banners are now rejected or hidden on both sides (`src/audit/consent-banners.ts`).
- WPBakery/Bricks rows that hold a collection (video, form, gallery…) plus loose images or buttons dropped them without a word: they are now carried as sections after the collection, and icons that have no place are reported in the coverage report.
- Coming-soon mode now purges cached pages when it is saved (a cached page never reaches the middleware), and the middleware reads the switch on every render so a stale isolate cannot re-cache the public page.
