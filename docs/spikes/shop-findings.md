# WooCommerce catalogue mode

**Date:** 2026-11-22 · **EmDash:** 1.5.0 (behaviour reused from `cpt-findings.md`; no new EmDash API) · **EmDash Exporter:** 1.2.0 · PLAN §8b.

Small WooCommerce shops migrate with their products as pages and an external checkout: no cart, checkout or customer accounts on EmDash. Shops above `shop.maxProducts` (default 200), or with subscriptions or memberships, keep stopping.

## What was built

| Piece | Where | What it does |
|---|---|---|
| Config | `src/config/schema.ts` `shop` | `{ mode: "catalogue", checkout: "external" \| "stripe-payment-links" \| "contact" (default external), currency?, contactPath?, maxProducts (200) }`. Unset on a WooCommerce site = the `shop` gate stays red. |
| Audit | `src/audit/shop.ts`, `src/phases/audit.ts`, `src/audit/fingerprint.ts` | WooCommerce found in the fingerprint → reads the public Store API (`/wp-json/wc/store/v1/products?per_page=100&page=N`, `X-WP-Total`): product types, variations, on sale, out of stock, stock tracking (only visible through `low_stock_remaining`), reviews, attributes, currency. Extensions from plugin folders (Subscriptions, Memberships, Bookings). Writes `snapshot/shop.json`, `reports/audit/shop.md` (facts + every decision). Gate `shop`; WooCommerce itself leaves `no-out-of-scope` once `shop` is set (Subscriptions/Memberships stay out of scope there too). |
| Extract | `src/phases/extract.ts` | Asks the Exporter for `product_variation` too (not a public type, so analyze does not list it; the content endpoint has no post type restriction: cpt-findings). Products come as any public type does. |
| Facts, decisions, product fields | `src/transform/shop.ts` | `exporterFacts` (every product and variation: `product_type` term, `_downloadable`, `_virtual`, `_manage_stock`, `_stock_status`, `_wc_review_count`, sale dates, catalogue visibility, attributes; coupons when `shop_coupon` was extracted). `shopDecisions` lists what catalogue mode does with each part (always: cart/checkout, accounts, orders, coupons, payments/tax/shipping; when present: variable, grouped, external, other types, bookings, downloads, virtual, stock, out of stock, sales, scheduled sales, reviews, attributes, hidden products). `shopBlockers`: products > maxProducts, subscriptions (type or plugin), memberships plugin. `productMeta` computes the collection's values as `woo:<field>` meta for the CPT mapper. |
| Transform | `src/phases/transform.ts`, `src/transform/cpt.ts` | `product` is decided `{ as: "collection", name: "products" }` with built-in fields (`BuiltinCollection`: fields first, archive at the shop page's address, only `product_cat`/`product_tag`/`product_brand` as taxonomies, `shop` settings). Internal taxonomies (`product_type`, `product_visibility`, …) are never collection taxonomies; `pa_*` attribute taxonomies are shown as fields and listed as such in the content inventory. WooCommerce pages (by `woocommerce_*_page_id` or their shortcode/block): the shop page becomes the listing, cart/checkout/my-account are not migrated and get `wpUrls.shop` redirects. Gates `shop` (same as the audit, with the Exporter's facts) and `shop-checkout` (currency, contact page for checkout "contact", products collection). `ir/shop.json`, coverage report → "Shop (WooCommerce)". `total_sales` counts as WooCommerce's own meta. |
| Redirects | `starter/src/utils/wp-urls.ts` | `rules.shop = { paths, to }`: the paths and everything under them (`/my-account/orders/`, `/checkout/order-received/…`) and any `?add-to-cart=` 301 to the listing; a real page at one of the paths still wins. Middleware and verify's `urls-accounted` use the same matcher. |
| Starter | `utils/shop.ts`, `components/collections/{ProductCard,ProductDetail}.astro`, `Archive.astro`, `Entry.astro`, `[...slug].astro`, `StructuredData.astro`, `Base.astro`, `llms.txt.ts` | Listing and category listings: product cards (picture, name, price with sale, "From" for variable, availability). Product page: pictures (featured + gallery), price, availability, SKU, short description, Buy button, then the description, attributes list and variations table. Buy button: `buy_url` (external checkout, Stripe Payment Link; external products always keep theirs), else the contact form `?product=<name>`; out of stock = disabled. JSON-LD: Product + Offer (simple) or AggregateOffer (variable), availability, joined to the WebPage node. llms.txt lists products after pages and posts. Sitemaps and search come from the collection (below). |
| Forms | `packages/forms/src/prefill.ts`, `starter/src/scripts/site.ts` | `?product=` fills a field named product/subject/service, else starts the first empty message box; other query values fill empty text fields of the same name. Never hidden, file, password, checkbox or radio fields. In the browser, so cached pages stay identical. |

## Verified (reused, no new EmDash behaviour)

- Everything the products collection needs is what `cpt-findings.md` verified on EmDash 1.5.0: collections with `urlPattern: "/{slug}"` (whole WordPress path as slug), field types `number`, `select` (options = values used, completed by `completeOptions`), `url` (http/https/mailto/tel or `/path`), `portableText`, `repeater` with flat `string`/`number`/`image` sub-fields; taxonomies with term archives at the live base; routable `hasSeo` collections listed in `/sitemap.xml` as `sitemap-<collection>.xml`; archives and term archives in `/sitemap/archives.xml`; string/text fields searchable (FTS).
- Exporter 1.2 (cpt-findings): `meta` is all post meta, unserialized (`_product_attributes` arrives as an object; the kit also parses a still-serialized string), `_edit_*`/`_wp_*` dropped; analyze lists public types only (so `product_variation` is requested explicitly).

## Assumptions not verified on a real shop yet

- **WooCommerce data shapes** come from WooCommerce's documented meta keys and Store API, exercised only with the synthetic fixture `test/fixtures/shop/site.json` (simple, on sale + out of stock, scheduled sale, variable with two variations, external with a download flag). Not run against a live WooCommerce site.
- **Store API** may be disabled or filtered by security plugins: the audit then reports "count unknown" and the transform gate (Exporter facts) decides.
- **`woocommerce_currency`** is not in the Exporter's options on every site: `shop.currency` in kit.config, else the Store API's `currency_code` from the audit; the `shop-checkout` gate asks when none is known.
- **Reviews**: the Exporter returns comments of type `comment`; WooCommerce reviews (`review`) are counted from `_wc_review_count` and reported, not carried as reviews.
- **Product blocks/shortcodes on other pages** (`[products]`, `wp:woocommerce/*`) have no section handler: they are reported by the adapters as unmapped (a `product_grid` section is a possible follow-up).
- Remote load and the rendered product pages were not run on a deployed site (local transform/seed/unit level only).
