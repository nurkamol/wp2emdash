# Outside-in monitor

Every delivered site checks itself (Site health): uptime, forms, links, certificates. That runs **inside the site's
own Worker**, so when the Worker, the Cloudflare account, DNS or the domain breaks, the site is down and nothing
alerts you. The monitor is the outside view: **one Cloudflare Worker the agency runs once for all its sites**, in its
own account, checking every site's home page every 5 minutes like a visitor.

Verified facts and limits: [spikes/monitor-findings.md](spikes/monitor-findings.md). Code: `packages/monitor`,
`src/commands/monitor.ts`.

## What it checks

| Check | How | Alert |
|---|---|---|
| Home page | GET through the public internet, redirects followed only on the same site (www ↔ apex), 10 s for the whole chain | — |
| Answer | 2xx, has a `<title>`, is not a Cloudflare error page (52x, 1xxx, "Worker threw exception") or a bot challenge, contains the optional keyword | — |
| Down | 2 failed checks in a row (≈ 5–10 minutes) | one message when it opens, one when the site answers again |
| Certificate | Certificate Transparency (Cert Spotter): the latest valid certificate for the host, once a day | daily while ≤ 14 days |
| Domain | RDAP (rdap.org → the registry), once a day | daily while ≤ 14 days |
| Weekly summary | Mondays 08:00 UTC, every site's state | off by default (`weeklySummary: true`) |

One message per tick for everything that happened (ten sites down in one Cloudflare incident is one email), at most
`maxAlertsPerDay` (20) messages a day; each incident is alerted once. If no channel can deliver, the message is
retried on the next two ticks. Messages name the site, its address, what failed and when — never page content.

Which sites: every `sites/<slug>/` with a deployed production — its **domain once `cloudflare.json` says
`production.live`**, else its `workers.dev` address — plus `extraUrls`, minus `exclude`. Rebuild after a go-live or a
new site.

## Where it lives

`pnpm wp2emdash monitor init` creates `monitor/` in the kit (gitignored — it names client domains and your alert
address). `--dir <path>` or `WP2EMDASH_MONITOR_DIR` puts it anywhere else, e.g. its own private repository.

```
monitor/
  monitor.config.json    ← yours: addresses, extra URLs, options (never overwritten)
  wrangler.jsonc         ← generated by `monitor build`
  package.json           ← generated (wrangler pinned to the kit's version)
  src/*.ts               ← generated: the Worker + the site list (src/monitor-config.ts)
```

`monitor.config.json` and the generated files hold **URLs and email addresses only**. Tokens and keys are Wrangler
secrets.

## Setup (the operator runs these; the kit never deploys)

1. **Pick the account.** Prefer a Cloudflare account the client sites do **not** run in (a free account of the agency is
   fine): then a suspended or misconfigured site account, a revoked token or an account-wide rule cannot silence the
   monitor too. It uses `*.workers.dev`, so it depends on no client zone or DNS. Put the account id in
   `accountId`. A Cloudflare-wide outage takes both down — see step 6 for the dead-man's switch.

2. **Configure.**

   ```bash
   pnpm wp2emdash monitor init
   # edit monitor/monitor.config.json
   ```

   ```json
   {
     "label": "Agency",
     "alertTo": ["ops@agency.example"],
     "from": "Site monitor <monitor@agency.example>",
     "emailProvider": "brevo",
     "telegramChatId": "-1001234567890",
     "extraUrls": ["https://agency.example", { "url": "https://legacy.example", "keyword": "Contact", "domain": "legacy.example", "expiry": false }],
     "keywords": { "acme": "Acme Studio" },
     "exclude": [],
     "timeoutSeconds": 10,
     "expiryWarnDays": 14,
     "maxAlertsPerDay": 20,
     "weeklySummary": false,
     "workerName": "wp2emdash-monitor",
     "accountId": "<32-hex account id>",
     "kvNamespaceId": "<from step 3>",
     "plan": "free"
   }
   ```

   `from` must be a sender verified at the email provider (the same Brevo account the sites use works).

3. **Create the KV namespace** (in the monitor's account) and put its id in `kvNamespaceId`:

   ```bash
   cd monitor && npx wrangler kv namespace create MONITOR_KV
   ```

4. **Build** the Worker from the current sites:

   ```bash
   pnpm wp2emdash monitor build        # lists the sites, what was skipped and why, and warnings
   ```

5. **Secrets** (typed at the prompt, never in files or the shell history):

   ```bash
   cd monitor
   npx wrangler secret put EMAIL_API_KEY       # Brevo API key (or the provider in emailProvider)
   npx wrangler secret put STATUS_TOKEN        # a long random string (openssl rand -hex 24): status page access
   npx wrangler secret put TELEGRAM_BOT_TOKEN  # optional (with telegramChatId)
   npx wrangler secret put SLACK_WEBHOOK_URL   # optional
   npx wrangler secret put HEARTBEAT_URL       # optional, step 6
   npx wrangler secret put CERTSPOTTER_API_KEY # optional: more than Cert Spotter's anonymous hourly quota
   ```

   The first `secret put` on a Worker that does not exist yet creates it; or deploy first (step 7) and set them after.

6. **Who watches the watcher (optional, recommended).** Create a check at a monitoring service outside Cloudflare that
   alerts when pings stop (e.g. healthchecks.io, period 5 minutes, grace 15) and set its ping URL as `HEARTBEAT_URL`.
   The monitor GETs it at the end of every tick.

7. **Deploy:**

   ```bash
   cd monitor && npx wrangler deploy
   ```

   Cron changes take up to 15 minutes to start. `npx wrangler tail` shows each tick's log line (counts and channel
   names only).

After a go-live or a new site: `pnpm wp2emdash monitor build && (cd monitor && npx wrangler deploy)`.

## Status page

`https://<workerName>.<your-subdomain>.workers.dev/?token=<STATUS_TOKEN>` — every site's state, since when, why,
certificate and domain expiry, and the monitor's own health (last write, alerts held by the cap, failing channels).
Without `STATUS_TOKEN` set, or with a wrong token, every request answers `404 Not found`: no public listing of client
domains. The page is `noindex`, `no-store`, `Referrer-Policy: no-referrer` and loads nothing external. A token in a URL
can end up in browser history: for a team, put **Cloudflare Access** (Zero Trust → Access → Applications → self-hosted,
the workers.dev hostname, your team's emails) in front of it and keep the token as a second lock.

## Costs and limits

- **Workers Free** fits about **20 sites** (50 subrequests per invocation: ≈ 2 per site per tick plus lookups and
  alerts; `monitor build` warns past that) and has 10 ms CPU per cron run, enough for a handful of sites. More: Workers
  Paid ($5/month, `plan: "paid"`), or two monitors with split lists.
- **KV writes**: the state is one key, written only when something changes plus once a day — at most 288 writes a day
  by construction, typically 1–3 (free plan: 1,000). Reads: 288 a day plus status page views.
- **Email**: one message per tick at most, ≤ 20 a day by default (Brevo free: 300/day).
- **What it cannot see**: pages other than the home page (Site health covers those from inside), forms, logged-in
  admin. A Cloudflare challenge served to the monitor counts as a failure (the agency should know a bot check is on;
  allow the monitor in that zone's WAF if it is intended). Certificate expiry comes from CT logs, not the certificate
  the edge serves; an expired one that is served fails the uptime check anyway. Domains without RDAP (e.g. .de) show
  "no RDAP for this domain". Cloudflare-wide outages need the heartbeat (step 6).

## Testing locally

```bash
cd monitor
npx wrangler dev                      # local; .dev.vars can hold STATUS_TOKEN=… for the page
curl "http://localhost:8787/cdn-cgi/local/scheduled?cron=*/5+*+*+*+*"    # runs one tick
```

Local runs make real GET requests to the sites in the list (and, in a site's daily slot, to Cert Spotter and RDAP).
