Move WordPress to EmDash. Prove nothing was lost.

wp2emdash migrates WordPress sites built with WPBakery, Salient, Gutenberg, the classic editor or Bricks to EmDash on Cloudflare Workers. It rebuilds pages as editable sections, carries posts, custom content, media, forms, SEO and every old URL, ships the site with an admin plugin suite, and stops at a gate whenever the result doesn't match the live site.

Eight phases. Each one ends in a gate.

A phase runs only when every earlier gate has passed or was accepted by the owner with a written reason. Gates are data — checks with ids and pass/fail — so the terminal, a CI job, the dashboard and Claude Code all read the same result.

  1. ready

    init

    Workspace, config, and the access & backup checklist the owner signs off.

  2. ready

    audit

    Crawl, screenshots, design tokens, menu motion, forms, integrations and builder fingerprint — public site only.

  3. ready

    extract

    Content, meta, SEO, menus, forms, plugin exports and media via the EmDash Exporter. Read-only.

  4. ready

    transform

    Builder layouts, posts and custom content → a typed section format, with coverage, text-conservation and content-type gates.

  5. ready

    scaffold

    EmDash project: section library, tokens, header & menu motion, plugin suite, performance package, client repo docs and CI.

  6. ready

    load

    Content, media, menus, taxonomies, redirects and settings through the EmDash API; an id-map makes reruns idempotent.

  7. ready

    verify

    Old vs new, URL by URL: text, SEO, every old address, links, forms, consent, cache, a11y and a visual diff per section.

  8. preflight ready

    cutover

    Read-only preflight and runbook, then the owner-approved switch with golive and a one-step rollback.

What it migrates

Builders are adapters on one shared core. Anything the kit doesn't carry shows up in the coverage report and keeps a gate red until the owner decides — nothing is dropped silently. The feature-by-feature matrix is in the parity audit.

An admin plugin suite in every site

Each migrated site ships with in-house EmDash plugins built by PixelKraft — native pages inside the client's own admin, no extra accounts or services. All but Form messages are on by default; each turns off with one line in the site's config.

SEO & Analytics

A score, Google preview and plain-words checklist next to every page; an SEO dashboard; Search Console and IndexNow; tracking codes by ID with conversion events; visits from Cloudflare Web Analytics.

Launch and operations

One Cloudflare environment per site by default: production, reviewed on its workers.dev address until launch. Staging is opt-in. Nothing public changes until the owner approves the switch.

Go live with one command

golive prints its plan and changes nothing until the owner says go: then Worker routes for the domain, a smoke test, a DNS comparison and the live flag. Alias domains get their own redirect step.

Rollback and bookmarks

golive --rollback removes exactly the routes it created. Every load into a live site and every go-live records a database bookmark first, with its restore command.

Publish to the client's repo

publish scans for secrets, creates the client's private GitHub repository and pushes the project, whose CI deploys it. Code changes after launch go through Workers preview URLs.

Dashboard and launch cockpit

Every site with its launch readiness, live runs, visual review, publish panel, environments and Worker secrets. Go-live steps need the domain typed and the owner's written approval.

Watched after launch

Site health checks uptime, indexability, form email, mail DNS and broken links from inside the site, and nightly backups keep 30 days plus 12 monthly copies.

The client's own Cloudflare

Production can run in the client's account: provision creates the database, storage, outbox and sessions bucket there, and the preflight checks the site and the domain share an account.

golive and publish are built and unit-tested against mocked Cloudflare and GitHub; they have not yet been run on a launch.

Performance and security, by default

Every generated site ships the same package, and verify measures it on the deployed site instead of assuming it.

Route cache and warm-up

Pages are kept in Cloudflare's cache next to visitors and purged within seconds of a publish; every deploy warms the cache. On staging a cached page answered in 80 ms instead of 0.8–1.8 s.

Responsive images, deferred video

Sized images through the Cloudflare Images binding, hashed brand files and fonts cached for a year, and background video attached only after the page has painted.

Content-Security-Policy

One provider table decides what may load: embeds, widgets and switched-on trackers by host, inline scripts on visitors' pages by hash. Trackers never load for signed-in editors or on test hosts.

Consent that holds

Analytics and marketing tags wait for the visitor's choice; verify checks in a real browser that nothing fires before it.

Sign-ins that stay signed in

Admin sessions live in a private, strongly consistent R2 bucket instead of Workers KV, which signed editors out at random.

Forms without spam or leaks

Turnstile, rate limiting and validation on a native endpoint; on health, legal or finance sites the owner picks a policy that keeps sensitive text out of the Worker and email.

Run it your way

One engine, three front-ends. pnpm wp2emdash asks once whether you want the terminal or the browser, and Claude Code works through the same commands — every decision ends up in versioned files, so a rerun reproduces it.

Terminal or browser

A guided terminal wizard, or a local dashboard on 127.0.0.1, token-protected. Gates are recorded in the terminal; the dashboard reviews, approves and takes secrets.

Claude Code built in

An MCP server and four skills run phases, read reports and explain red gates. Claude proposes changes instead of making them: each one waits in an approval queue for a person.

Secrets stay put

Keys go into a write-only form or .env, never into chat or logs. The dashboard shows only whether a key is set and a short fingerprint; every report is scrubbed.

Tested on real sites

Every adapter is built against a real client site, not a demo. The pipeline has run end to end on a real WPBakery/Salient site and a real Bricks site; one launch was switched by hand before the golive command existed. Client content never enters the kit repository — test fixtures are synthetic.

Get started

Requires Node.js 24+ and pnpm. Generated sites deploy to Cloudflare Workers (Workers Paid plan) on the latest Astro that EmDash supports.

# install
git clone https://github.com/OWNER/wp2emdash
cd wp2emdash && pnpm install
cp .env.example .env          # Cloudflare token
pnpm wp2emdash doctor

# create a site workspace (or just run `pnpm wp2emdash`: terminal wizard or browser dashboard)
pnpm wp2emdash init --slug acme --name "Acme Clinic" --source https://www.example.com

# run the phases in order; each stops at its gate
pnpm wp2emdash run acme audit
pnpm wp2emdash run acme extract
pnpm wp2emdash run acme transform
pnpm wp2emdash run acme scaffold

# create the Cloudflare resources, then load and compare with the live site
pnpm wp2emdash provision acme
pnpm wp2emdash run acme load
pnpm wp2emdash run acme verify

# check everything the switch needs (read-only), then plan the launch
pnpm wp2emdash run acme cutover
pnpm wp2emdash golive acme       # prints the plan; --yes only with the owner's go-ahead
