Move WordPress to EmDash. Prove nothing was lost.

wp2emdash rebuilds WPBakery, Salient, Gutenberg, classic and Bricks sites as editable EmDash sections on Cloudflare Workers, carries content, media, forms, SEO and every old URL, and stops at a gate whenever the result doesn’t match the live site.

Pipeline

Eight phases. Each ends in a gate.#

A phase runs only when every earlier gate has passed, or was accepted by the owner with a written reason. Gates are data — checks with an id and a pass/fail — so the terminal, CI, the dashboard and Claude Code read the same result.

  1. 01

    init

    Workspace, site config, and the access and backup checklist the owner signs off.

    Gate proves

    Every access item the migration needs is in hand before anything is read.

    access-missing
  2. 02

    audit

    Crawl, screenshots, design tokens, menu motion, forms, integrations and the builder fingerprint. Public site only.

    Gate proves

    The site is reachable, its builder is supported, and sensitive-data handling is decided.

    home-reachablebuilders-supportedsensitive-data-flagscreenshots
  3. 03

    extract

    Content, meta, SEO, menus, forms, plugin exports and media through the EmDash Exporter. Read-only.

    Gate proves

    Fetched counts match WordPress’s own totals and every page the audit found is in the export.

    counts-matchmedia-downloadedaudit-crosscheck
  4. 04

    transform

    Builder layouts, posts and custom content into a typed section format.

    Gate proves

    No content is unmapped, the live page text is all there, and every post type is migrated or decided.

    unmappedtext-conservationcontent-types-handled
  5. 05

    scaffold

    The EmDash project: section library, tokens, header and menu motion, plugin suite, performance package, docs and CI.

    Gate proves

    Every section type has a component, the seed passes EmDash’s validator and the project type-checks.

    section-componentsseed-validtypecheck
  6. 06

    load

    Content, media, menus, taxonomies, redirects and settings through the EmDash API. An id-map makes reruns idempotent.

    Gate proves

    Entry counts equal the source, no WordPress URLs or shortcodes remain, and every page renders.

    countsid-mapno-wordpress-leftoversrender
  7. 07

    verify

    Old against new, URL by URL: text, SEO, links, forms, consent, cache, accessibility and a visual diff per section.

    Gate proves

    Every old address is accounted for, SEO is identical, forms submit and nothing tracks before consent.

    urls-accountedseo-titleforms-submitconsent-runtimea11y
  8. 08

    cutover

    A read-only preflight and runbook, then the owner-approved switch with golive and a one-step rollback.

    Gate proves

    Worker and domain share an account, no other route holds the domain, and mail records are snapshotted.

    same-accountroutes-freedns-snapshotindexable

Exit codes are part of the contract: 0 passed, 2 gate failed, 3 not built yet, 1 error. Only the owner can accept a failed gate, with wp2emdash accept --reason, and the reason is logged.

Dashboard

A migration, step by step, in the browser#

pnpm wp2emdash ui opens a local dashboard for everything a terminal can’t show well: where each site stands, screenshots and diffs, changes waiting for approval, and the launch. Phases still run from the terminal or the wizard, and the dashboard streams them live. The pictures below are drawings of the real screens, filled with made-up data.

  1. Open the portfolio

    Run pnpm wp2emdash ui. It serves on 127.0.0.1 only, behind a token that is new on every start, and opens your browser.

    Every site in sites/ gets a card: the eight phases as a bar, a launch-readiness score, what blocks launch, the last run and the exact command to run next, with a copy button.

  2. See what blocks launch

    A site’s Overview shows every gate (passed, accepted with the owner’s reason, or failed) and turns the failing checks into a to-do list. Each item has the command or the screen that fixes it.

    The readiness score is simply the share of launch checks that pass: pipeline gates, verify checks and the cutover preflight.

  3. Run a phase and watch it live

    Run the phase from the terminal or the wizard. The dashboard streams its steps, item counts and log as they happen, and keeps every past run on the Runs tab.

    Gates are data, so the terminal, CI, Claude Code and the dashboard all show the same result.

  4. Compare WordPress and EmDash

    Every page at phone, tablet and desktop widths: drag the slider, view them side by side, or show only the changed pixels. A table lists the difference section by section.

    Approve or reject a difference with a reason, and a dated row goes into decisions.md. That never passes the gate on its own: the owner still accepts it with wp2emdash accept.

  5. Approve the fixes

    Click a row on the WordPress screenshot in the Section inspector to see its source and what it became. “Change section type” or “Drop row” writes a proposal. Claude Code’s suggestions land in the same queue.

    Each proposal shows the exact change to overrides.ts or decisions.md. Approving applies it and can start a preview run of transform, scaffold or verify. It never starts load or cutover.

  6. Hand over keys safely

    The Secrets tab takes each key in a write-only form: the migration key, the app password, Cloudflare and email keys. Values go to the site’s .env and are never shown again, only “set” and a short fingerprint.

    The owner’s checklist (ACCESS.md) is shown next to it, so missing access is visible before the first phase runs.

  7. Launch with the owner’s approval

    The Launch cockpit shows the cutover preflight, the runbook and each step: go live, alias redirects and rollback. “Show plan” lists exactly what will change and changes nothing.

    A step runs only after you type the production domain, tick that the owner approved it in writing and record who approved it and when. It runs the same golive command as the terminal. DNS is never changed.

After launch: the Fleet page lists every site with the kit version it was built with, its last change, its last upgrade check and open owner to-dos. The dashboard writes only what you decide in it: decisions, approved proposals, keys and the owner-approved launch steps. It never accepts a gate and never changes DNS.

Launch & operations

Nothing public changes until the owner says go#

One Cloudflare environment per site by default: production, reviewed on its workers.dev address until launch. Staging is opt-in. Production can live in the client’s own Cloudflare account.

  1. provision

    Create resources

    Database, storage, outbox and sessions bucket, in the account that owns the domain.

  2. run load

    Load content

    Idempotent writes through the EmDash API. Loads into a live site record a database bookmark first.

  3. run verify

    Compare with live

    The deployed site against the WordPress original, URL by URL, at phone, tablet and desktop widths.

  4. golive

    Switch the domain

    Prints its plan and changes nothing until the owner approves: routes, smoke test, DNS comparison, live flag.

  5. golive --rollback

    Watch or roll back

    Rollback removes exactly the routes it created. Site health and nightly backups watch the site after launch.

Honest status: golive and publish are built and unit-tested against mocked Cloudflare and GitHub. They have not yet been run on a launch.

Publish to the client’s repo
publish scans for secrets, creates a private GitHub repository and pushes the project; its CI deploys it.
Launch cockpit
Readiness per site, live runs, visual review, environments and Worker secrets. Go-live needs the domain typed and the owner’s written approval (see the dashboard).
Bookmarks before writes
Every load into a live site and every go-live records a D1 Time Travel bookmark, with its restore command.

Operations

Built for an agency with many sites#

From the first quote to years of updates: each tool reads before it writes, and nothing touches production without the owner’s approval.

  • estimate <url>

    Quote a prospect

    Reads a prospect’s public WordPress site politely (no login) and writes a branded client report plus an internal effort sheet: builder, plugins, forms, speed, blockers and an hours range from rules you tune.

  • deploy check

    Roll back a bad deploy

    After every deploy the site is checked like a visitor would: every page, its fonts, stylesheets, scripts and hero picture. If anything is broken, the Worker is rolled back to the version that was live before.

  • upgrade <slug>

    Upgrade with proof

    Captures every live page, rebuilds on the new kit, deploys staging if you ask, and compares page by page. It prints the production command for the owner and never runs it; --verify checks production afterwards.

  • fleet

    Every site at a glance

    One table with the kit version each site was built with, its last change, its last upgrade check, live status and owner to-dos. fleet upgrade-prs opens upgrade pull requests on a separate branch, never on main.

  • monitor

    Watch from the outside

    One small Worker loads every site’s home page every 5 minutes and checks certificate and domain expiry daily. It alerts by email, Telegram or Slack, even when a site’s own Worker or account is down.

  • e2e: real WordPress

    Tested on real WordPress, nightly

    A throwaway WordPress in CI with Elementor, WooCommerce, Polylang, Contact Form 7 and Fluent Forms runs through the whole pipeline every night. Its first runs caught bugs that made-up fixtures could not: a build failure for new projects, lost quote text and every translated page answering 404.

  • sync-staging <slug>

    Test on real content

    Copies production’s content to staging from an explicit list of tables, without users, form messages or secrets. It shows a plan first and bookmarks staging before writing.

Defaults

Performance and security, measured#

Every generated site ships the same package, and verify measures it on the deployed site instead of assuming it.

Route cache
Pages kept in Cloudflare’s cache next to visitors, purged within seconds of a publish and warmed on deploy. On staging a cached page answered in 80 ms instead of 0.8–1.8 s.
Images and video
Sized images through the Cloudflare Images binding, brand files and fonts cached for a year, background video attached after first paint.
Content-Security-Policy
One provider table decides what may load; inline scripts on visitor pages by hash. Trackers never load for signed-in editors or on test hosts.
Consent that holds
Analytics and marketing tags wait for the visitor’s choice; verify checks in a real browser that nothing fires before it.
Sessions on R2
Admin sessions in a private, strongly consistent R2 bucket instead of Workers KV, which signed editors out at random.
Forms without leaks
Turnstile, rate limiting and validation on a native endpoint. On health, legal or finance sites the owner picks a policy that keeps sensitive text out of the Worker and email.

Workflow

One engine, three front-ends#

Every decision ends up in versioned files — overrides.ts, decisions.md — so a full rerun from the raw exports reproduces the result.

Terminal
A guided wizard: create a site, run each phase, record gates. --json on every command for scripts and CI.
Browser dashboard
Local on 127.0.0.1, token-protected. Reviews, approves, takes secrets in a write-only form and shows only their fingerprint. See it step by step.
Claude Code
An MCP server and four skills run phases and explain red gates. Proposed changes wait in an approval queue for a person.

Get started

From clone to a verified site#

Requires Node.js 24+ and pnpm. Generated sites deploy to Cloudflare Workers (Workers Paid plan) on the latest Astro that EmDash supports.

terminal 
# install and check prerequisites
git clone https://github.com/nurkamol/wp2emdash
cd wp2emdash && pnpm install
cp .env.example .env          # Cloudflare token
pnpm wp2emdash doctor

# a site workspace (or just `pnpm wp2emdash`)
pnpm wp2emdash init --slug example --name "Example" \
  --source https://www.example.com

# each phase stops at its gate
pnpm wp2emdash run example audit
pnpm wp2emdash run example extract
pnpm wp2emdash run example transform
pnpm wp2emdash run example scaffold
pnpm wp2emdash provision example
pnpm wp2emdash run example load
pnpm wp2emdash run example verify
pnpm wp2emdash run example cutover   # read-only preflight
